# ADR 0007 — Race strategy seams belong to their bounded contexts
- **Status:** Proposed (design for NEXT #7; owner acceptance is required before implementation).
- **Date:** 2026-10-09
- **Context:** Atlantis has 241 files branching on race. The target is a modular monolith with six bounded contexts and dependencies inward (`DOCS/ARCHITECTURE-CONTEXT-MAP.md`, ADR 0001). Race is an orthogonal strategy dimension, not a seventh context. The code already has one successful local precedent: `RacePlacementStrategy` in `atlantis.placement.core`, with Protoss/Terran/Zerg implementations. Production V2 still branches on `We.protoss/terran/zerg` in goal generation and snapshot assembly. Its engine is currently a static singleton in `ProductionOrdersCommander`; the legacy `DynamicBuildingsCommander` selects race-specific commanders at the production composition boundary.
- **Problem:** moving race `if` statements into one global `RaceStrategy` would make a new God object and couple unrelated policies (placement, production, scouting, combat). Copying the existing 241 branches into per-race classes would preserve the branching with extra indirection. Race-specific behavior should be owned by the context whose policy differs.

## Decision (proposed)

1. **Use context-local strategy ports, not one application-wide `RaceStrategy`.** Each bounded context introduces a strategy only when its own race-dependent decisions are migrated. `Placement` keeps `RacePlacementStrategy`; `Production` may introduce a narrow `ProductionRacePolicy`. Combat, Scouting, and Economy get their own ports only when a concrete migration needs them. Do not add empty or speculative strategy interfaces.
2. **Resolve the implementation once at the composition boundary.** The Production pilot removes static `V2_ENGINE` ownership from `ProductionOrdersCommander` and creates the engine as an instance with an injected immutable `ProductionRacePolicy`; that commander is the current application composition point. The pilot adds a package-local `ProductionRacePolicy.forRace(Race)` selection only if placing the selector at bootstrap is not possible without crossing existing dependency rules; prefer having the composition point select from `AtlantisRaceConfig.MY_RACE`. `ProductionEngine` and `GameStateSnapshot` receive the policy through constructors. `DynamicGoals` and `PullForwardGoals` take the policy as explicit input to their pure goal-generation methods. None of those per-frame decisions reads `We.*()` or `AtlantisRaceConfig` to rediscover race. No static strategy cache or mutable global selector.
3. **First pilot is Production V2, behavior-neutral and deliberately narrow.** `ProductionRacePolicy` exposes exactly five type identities used by generic goal/snapshot code: worker, baseline army unit, base, supply provider, and gas building. It does not decide priorities, resource arbitration, or strategic targets. Pin each mapping for Protoss, Terran, and Zerg before swapping selectors. Keep the Protoss-only cannon fortification contributor (`DynamicGoals.addFortificationGoals`) as an explicitly documented, un-migrated policy branch in this pilot; it is a strategy/placement policy, not a sixth type identity. Measuring branch-site reduction must count only the exact selector sites removed, not claim all Production V2 race differences were migrated. Other differences remain measured follow-up decisions, not hidden in a growing interface.
4. **No physical package migration is part of the pilot.** Keep the port and implementations next to the Production V2 application policy until Stage I. `Production` may depend on the core type API and its own strategy API; the bootstrap wires implementations. The ArchUnit baseline must not grow.
5. **Placement remains separate.** `RacePlacementStrategy` answers spatial questions (availability, templates, ranking), while `ProductionRacePolicy` answers which producibles the production goal layer names. Neither imports the other's implementation. The hardcoded Protoss Pylon prerequisite in `UnitProducible` is an existing parity gap to inventory for the placement/production integration; this ADR does not silently broaden the production policy to take ownership of placement mechanics.

## First implementation slice (NEXT #8)

- Add the narrow Production V2 port and three explicit immutable implementations. Resolve one at the existing `ProductionOrdersCommander` composition point from the authoritative `AtlantisRaceConfig.MY_RACE`; the scheduler must not select race policy.
- Change `DynamicGoals` and `PullForwardGoals` to accept the policy as an input, and pass it through `ProductionEngine`/`GameStateSnapshot`. The five selectors to migrate are worker, baseline army, base, supply-provider and gas-building type selection. Keep cannon fortification and the hardcoded Psi prerequisite outside this pilot. Do not change priorities, thresholds, income assumptions, build-order parsing, or dispatcher behavior.
- Add deterministic tests for each race mapping and for representative generated goal identities. Compare the old and new goal lists for equivalent snapshots before deleting the old branches.
- Measure the production branch-site count before and after with the same source query, and run the fast suite plus ArchUnit. The acceptance bar for the pilot is: no new ArchUnit edges, unchanged goal identities/order in the characterization tests, and fewer production race branches. No game behavior change is claimed from compilation alone.
- Keep this slice incremental and playable. If the old and new paths cannot be compared deterministically, stop before switching the live composition and return with the missing test seam.

## Non-goals
- No repository-wide conversion of all 241 race branches in one change.
- No global `RaceStrategy`, race enum switch utility, or broad interface returning arbitrary policy decisions.
- No edits to combat/placement behavior under a Production ticket.
- No removal of `We.*()` outside the pilot scope, no static strategy cache, no package moves.
- No assumption that the three races are symmetric; each context documents its own real differences.

## Consequences and open decisions
- Each strategy interface remains small and named for its context, while bootstrap owns selection. This adds one injection point per migrated context but prevents unrelated policy axes from accumulating in one class.
- Production V2 currently exposes static goal-generation methods and is owned by a static engine singleton. #8 must first make the race policy an explicit immutable input to goal generation, snapshot assembly, and an instance-owned engine. Do not preserve compatibility by adding a mutable static current-race/current-policy field.
- Race selection source must be the same authoritative source already used by startup (`AtlantisRaceConfig.MY_RACE`, populated from the actual game); startup mismatch remains a configuration diagnostic, not a second strategy selector. Because that field is static, read it exactly once when `ProductionOrdersCommander` constructs its engine; never retain it as mutable strategy state.
- Owner review is required because this ADR chooses a design direction. Until accepted, it does not authorize the #8 code migration.
